# Протокол разработки Data Pipeline (Category-Operator-Determination)

## Основные принципы архитектуры ETL
1. **Idempotency (Идемпотентность):** Повторный запуск пайплайна с теми же данными не должен приводить к дублированию карточек на маркетплейсе. Реализовать проверку существования артикула.
2. **Error Isolation & Logging:** Если один товар из пачки вызвал ошибку (например, битая картинка), конвейер не должен падать целиком. Ошибка изолируется, логируется, а пайплайн переходит к следующему элементу.
3. **No Placeholders:** Весь код на Python и структуры n8n должны быть финальными, без комментариев вроде `# реализовать обработку позже`.

## Ограничения и лимиты (Rate Limiting)
- **API маркетплейсов:** Запросы на создание карточек должны идти пачками (Batching) с задержкой, чтобы не поймать блокировку (HTTP 429).
- **Gemini API:** Использовать асинхронные вызовы (Async/Await) на бэкенде FastAPI для параллельной обработки элементов, если это позволяет бесплатный лимит модели `gemini-3.1-flash-lite`.

## Стек проекта
- **Оркестратор:** n8n (Self-hosted, Local node).
- **Бэкенд-автоматизация:** Python, FastAPI, Pydantic v2, BeautifulSoup4 (парсинг мета-данных).
- **AI-движок:** Gemini 3.1 Flash Lite API (структурированная JSON-уникализация контента).

## Структура Выходных Данных ИИ
Каждый обработанный товар должен строго валидироваться через Pydantic-схему:
- `original_sku`: исходный артикул конкурента
- `clean_title`: уникальный SEO-заголовок (без чужих брендов)
- `clean_description`: переписанный b2c/b2b-текст
- `extracted_specs`: словарь (dict) очищенных характеристик товара
- `media_urls`: список ссылок на изображения
